# 真实货代订舱业务对照评估（V1）

> 目的：对照现实中海运出口订舱的标准操作流程，评估本系统 V1 的业务流程覆盖度，识别差距。
> 调研依据：公开的行业操作规范与实操资料（货代海运出口全流程、订舱指南等），结合本仓库 PRD/技术设计/进度日志。
> 日期：2026-08-31
> 结论先行：**主链路（查价→报价→订舱→SO→运输→跟踪→单证→账单）与真实业务高度吻合，骨架正确；主要差距在截关时间、贸易条款/预付到付、提单草稿确认与电放、月结对账单、改船/甩柜异常处理等操作细节。**

---

## 1. 真实业务标准流程（业界通行的 8 步）

```
① 询价比价（客户提需求：POL/POD/货好时间/柜型柜量/特殊需求）
② 确认报价（海运费+附加费+有效期，警惕低海运费高附加费）
③ 提交订舱委托 Booking Note（发货人/收货人/货名/件毛体/柜型柜量/贸易条款/预付到付）
④ 船司放舱 → 核对 SO（船名航次/截关截单截港时间/提柜地点/ETD/柜型）
⑤ 提柜装箱（拖车凭 SO 提空柜→工厂装货→封柜→重柜返港，记封条号）
⑥ 报关放行（发票/装箱单/委托书，三单数据必须一致）
⑦ 提单确认与签发（客户核对草稿 BL → 付运费 → 正本/电放/海运单）
⑧ 费用结算与后续跟踪（费用清单确认→开票→付款；跟踪至目的港）
```

## 2. 逐环节对照表

| 环节 | 真实业务要求 | 本系统现状 | 评价 |
| --- | --- | --- | --- |
| ① 询价比价 | 按 POL/POD/ETD/箱型查价，比较海运费+附加费总价 | `GET /portal/rates` 支持 POL/POD/ETD 范围/箱型/Carrier；附加费按 V1 规则汇总进报价 | ✅ 吻合 |
| ② 报价 | 明细、有效期、PDF | Quote 快照 + PDF 异步生成 + 销售手工改价 + 有效期/过期 | ✅ 吻合，且快照设计正确 |
| ③ 订舱委托 | 发货人/收货人/通知人、货名、件毛体、柜型柜量、贸易条款（FOB/CIF 等）、运费预付/到付 | Booking 从 Accepted Quote 转单，复制航线/船司/ETD/箱型，客户补货物、联系人、箱量 | ⚠️ 大体吻合，但缺 **贸易条款（Incoterms）** 和 **运费预付/到付** 字段；收发货人结构化信息较薄 |
| ④ 舱位确认与 SO | SO 含船名航次、**截关/截单/截港时间**、提柜地点、ETD | Booking `CONFIRMED` 后 Operation 上传 SO 文件 → `SO_RELEASED` | ⚠️ 流程吻合，但 SO 的 **截关时间（Customs/SI/CY Cutoff）** 和提柜地点没有结构化字段——这是真实操作中最关键的时间线 |
| ⑤ 提柜装箱拖车 | 拖车安排、柜号封条号核对、进港 | TrackingEvent 含提柜/进港节点，Container 有柜号/封条/VGM | ✅ 节点吻合（拖车调度本身 V1 不做，合理） |
| ⑥ 报关 | 客户提供发票/装箱单，货代报送海关 | 明确不做（V1 范围外） | ✅ 有意取舍，符合 PRD |
| ⑦ 提单确认与签发 | 客户核对 **BL 草稿** → 确认 → 付款后签发 **正本/电放/海运单** | DRAFT_BL/FINAL_BL 上传、版本化 SUPERSEDED、客户下载 | ⚠️ 文件管理吻合，但缺 **客户确认 BL 草稿的交互动作** 和 **出单方式（正本/电放/SWB）** 字段；BL 结构化字段（收发货人/件毛体/唛头）未建模型 |
| ⑧ 费用结算 | 费用清单确认→开票→付款→放单；**月结对账单** 很常见 | Invoice：Draft→Issued→Customer Confirmed→Paid，附件上传 | ⚠️ 单票账单闭环完整；缺 **按月汇总对账单（月结 Statement）**——国内货代绝大多数客户是月结 |
| ⑨ 异常处理 | **甩柜（Rollover）、改船、超堆期/柜租费**、取消订舱费用确认 | Booking/Shipment 可受控取消 | ⚠️ 缺改船/换船记录（真实旺季高频）；超期费未建模 |
| ⑩ 通知与跟踪 | 船司官网/货代系统查实时位置 | 人工录入 TrackingEvent 时间线 | ✅ 符合 V1 定位（不做 AIS 实时追踪是有意取舍） |

## 3. 总体判断

**符合度：约 80% 的核心流程吻合，方向正确。**

系统抓住了真实业务的本质链条（报价快照、订舱审核、SO 放柜、节点跟踪、账单确认），且刻意不做报关/EDI/实时追踪，这个取舍与中小货代"人工操作+软件透明化"的现实一致——真实中小货代本来就是人工报关、微信传文件，门户价值正是在于把这些环节线上化。

**关键差距（按真实使用影响排序）：**

1. **截关/截单/截港时间（Cutoff Times）**——没有这几个时间，客户无法在门户上知道"最晚什么时候送资料/进港"，操作也无法据此催促客户；这是 SO 上客户最关心的信息之一。影响：★★★
2. **Incoterms 与运费预付/到付**——FOB 指定货是国内出口的主力场景（收货人指定货代），没有贸易条款无法区分谁付钱、怎么开账单。影响：★★★
3. **月结对账单（Statement）**——真实客户几乎都按月对账一次付清，单票 Invoice 逐票确认在月结场景下会很繁琐。影响：★★★
4. **BL 草稿确认动作与出单方式（正本/电放/SWB）**——真实流程中客户确认 BL 草稿是一个明确的业务动作（改单还要收费），目前系统只是文件上传下载。影响：★★
5. **改船/甩柜与超期费**——旺季高频异常，目前只有取消。影响：★★
6. **收发货人/通知人结构化数据**——Booking 只有 shipper 一个方向的信息，BL 制单所需的 Consignee/Notify Party 未建模。影响：★★

**建议：** 以上差距均不改变 V1 主链路的数据模型骨架（Rate→Quote→Booking→Shipment→Invoice 关系不受影响），可作为 V1.5/V2 Backlog 逐项排期；若试点前只能补一项，优先补 **Cutoff 时间字段 + Incoterms/预付到付**（改动小、客户感知强）。不建议在 UAT 前临时扩大 V1 范围。
