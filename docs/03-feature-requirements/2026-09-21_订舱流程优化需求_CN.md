# 订舱流程优化需求

> 日期：2026-09-21  
> 状态：第一轮代码已实施，浏览器与业务验收待完成；第二轮仍为提案。[实施与验证记录](../04-testing-acceptance/2026-09-22_订舱流程优化实施与验证_CN.md)。
> 适用范围：海运 FCL，Accepted Quote → Booking → 订舱确认单 → Basic Shipment。
> 目标：在现有订舱主链上补齐委托、办理、确认、异常和交接，减少客户追问及操作员重复录入。

## 1. 背景与结论

客户反馈现有订舱流程过于粗略。对照实际海运整柜流程，当前系统已具备正常路径的状态控制，但对“谁负责办理、正在等待什么、资料如何对外使用、发生变化如何处理、订舱后如何交接”的支持不足。

本次优化保留现有领域对象和订舱主状态机，优先接通已有能力，再分阶段补充异常与履约协同。不能将实际海运全流程图直接转成一张不断增加状态的 Booking 表。

本次文档依据为代码及文档静态核对，未执行运行环境验收。工作区已有其他进行中的变更，实施前必须复核实际代码及迁移，本文所列现状不能替代实施前检查。

## 3. 已有能力与差距

| 环节 | 已有能力 | 本次识别的不足 |
| --- | --- | --- |
| 报价转订舱 | 继承报价航线、箱型箱量等信息，补充货物、发货人和联系人 | 缺少面向提交与线下办理的完整委托交付物 |
| 资料审核 | 退回补料、重新提交、审核通过、审核留痕 | 需让缺项、当前动作和处理结果更连贯 |
| 对外订舱 | 记录船司／代理、参考号和备注 | 缺少业务负责人、预计回复时间及持续跟进结果 |
| 订舱确认单 | 内部登记、独立发布、版本机制、客户下载 | 后端已有 ETA、CY/SI/VGM 截止时间、码头字段，当前登记弹窗未提供对应录入项 |
| 取消 | 部分未完成状态可直接取消，BOOKED 无普通取消转换 | 不支持申请、外部确认及关联运输处理的闭环 |
| 变更 | 草稿／退回阶段允许编辑，订舱确认单 有版本机制 | 提交后的业务变更缺少原因、影响与确认路径 |
| 运输交接 | 有效内部 订舱确认单 后可创建运输记录 | 提箱、拖车、装柜安排及执行责任未形成完整交接 |

评估入口：`apps/api/src/modules/bookings/`、`apps/web/app/portal/bookings/`、`apps/web/app/admin/bookings/`、`prisma/schema.prisma`。已有版本、字段或状态不等于相应业务闭环已实现。

## 4. 目标流程和对象边界

正常路径：

```text
已接受报价
→ 订舱草稿：继承已知资料，补充缺项
→ 核对并提交订舱委托
→ 操作审核：通过 / 退回补料 / 业务拒绝
→ 线下向船司或代理提交，系统记录执行信息
→ 跟进回复
→ 收到 订舱确认单，登记结构化信息及附件
→ 内部核对，按需发布给客户
→ 创建／关联运输，交接后续安排
```

创建运输可在 订舱确认单 内部登记后进行，不必等待客户发布或客户阅读文件。

| 对象 | 负责表达 |
| --- | --- |
| Quote | 已接受的价格、服务范围与商务条件 |
| Booking | 客户订舱委托、审核及对外办理过程 |
| 订舱确认单 | 船司／代理返回的确认结果、有效版本与截止信息 |
| Shipment | 实际运输执行、时间及后续交接 |

客户申请的服务不自动成为货代承诺。操作员不能通过修改 Booking 默默改变已接受报价。第一轮继续关联展示报价条款，结构化服务责任模型归第二轮评审。

## 6. 第一轮详细需求

### A1. 可核对、可追溯的订舱委托

客户提交前应能核对一份完整委托摘要，包括：

- 来源报价及已接受条款入口。
- 航线、船司、箱型箱量、计划船期及货好／装货日期；计划日期不得标成船司已确认日期。
- 货物明细、包装、件数、毛重、体积、危险品及特殊要求。
- 发货人和本票订舱联系人。
- 客户申请服务及提送货地点；明确其与已确认报价服务的区别。

复用已知数据，只要求补充真正缺少的信息。保存草稿与正式提交继续分开，沿用现有服务端必填校验，不在本轮静默放宽提交标准。收货人、通知人、运费预付／到付是否属于首轮必填，不凭行业惯例追加，见第 10 节待确认项。

正式提交成功时保留该次委托版本、提交人和提交时间；退回修改后重新提交形成新版本，历史版本不可被覆盖。快照不包含成本、供应商协议或内部备注，不因之后修改客户档案而改变历史内容。

提供可打印／导出的委托单，默认使用最近一次已提交版本，带订舱号、关联报价号、版本及提交时间。草稿如支持预览，必须标明“草稿／未提交”。该文件用于客户核对和线下业务沟通，不宣称已直接向船司发送，也不等同于每家船司的专用模板。

### A2. 订舱确认单 结构化录入与核对

在现有登记界面补齐如下信息：

| 信息 | 要求 |
| --- | --- |
| 订舱确认单 编号、来源类型／名称、船司 | 保留现有能力，可从前一步带入并核对 |
| 船名、航次、ETD | 保留现有能力；与报价计划日期分别表达 |
| ETA | 补齐录入与回显 |
| CY 截止、SI 截止、VGM 截止 | 补齐精确到时间的录入、回显和客户展示 |
| 码头 | 补齐录入与回显 |
| 订舱确认单 接收时间 | 允许记录实际收到的时间，与系统上传时间区分 |
| 原始文件 | 保持格式、大小及存储权限校验 |

非必填数据未知时允许为空，显示“待船司确认／未提供”，不得用报价日期或当前时间冒充事实。截止时间保存 UTC，输入及显示必须明确业务时区，不能依赖服务器本地时区。不得将 CY、SI、VGM 合并为一个笼统“截关时间”。

日期格式和非法值由服务端校验；截止时间与 ETD 的可疑关系提示核对，不在未确认规则前将所有顺序差异硬性拒绝。

内部保存后客户不可见；发布前展示结构化信息与附件核对摘要。保留现有版本和发布机制，修订已发布 订舱确认单 不覆盖旧记录。客户默认使用有效已发布版本，内部可追溯历史；新版本尚未发布时不得提前暴露。

截止信息第一轮只做清楚展示和基于已有数据的临近／已过提示，不新增定时提醒服务。截止时间已过不自动代表业务逾期或操作未完成。

### A3. 阶段提示与下一步

客户详情优先回答当前进度、需要自己做什么、正在等待谁，再提供资料、订舱确认单 和运输入口。

| 当前状态 | 客户提示方向 | 内部主要动作 |
| --- | --- | --- |
| DRAFT | 补充资料并提交订舱 | 查看草稿资料，不能假定已受理 |
| SUBMITTED | 已提交，等待货代核对 | 审核、退回补料或业务拒绝 |
| REVISION_REQUIRED | 列明需要补充的内容及入口 | 等待客户重提 |
| APPROVED | 货代正在办理订舱 | 线下提交船司／代理并登记 |
| BOOKING_SUBMITTED | 已提交承运方，等待回复 | 跟进回复、登记 订舱确认单 |
| BOOKED | 已取得舱位确认，按实际发布／建档情况提供入口 | 核对／发布 订舱确认单、创建或查看运输 |
| REJECTED / CANCELLED | 显示客户可见原因与结果 | 不再提示沿正常主链继续 |

“已收到 订舱确认单 但未发布”和“还未收到 订舱确认单”应正确区分；客户不能下载内部文件。数据加载失败不得显示成无 订舱确认单 或无运输。客户不需要理解内部枚举值，不因未阅读 订舱确认单 被阻止后续办理。

### A4. 订舱确认单 到运输的信息继承

创建运输仍要求 BOOKED 且存在有效内部 订舱确认单。服务端选用当前有效 订舱确认单，初始化船司、船名、航次、ETD、ETA；不得仅依赖浏览器传入值或无提示地回退到报价计划船期。

对 订舱确认单 缺失字段保留“待补充”；确需采用 Booking 计划信息时明确标注来源，不能包装成已确认事实。已有运输时提供查看入口，防止重复建档。

订舱确认单 更新时不得静默覆盖运输已经人工核实的字段，尤其不得影响 ATD／ATA。第一轮至少提供差异提示和受控核对更新，记录修改者及前后值。订舱确认单 版本、运输信息和客户所见版本之间的差异必须可解释。

## 7. 第二轮业务提案

以下是拟议业务规则，需在实施前确定细节及数据设计，不能直接视为已批准的新状态枚举。

### B1. 办理负责人和跟进

每票可指定订舱负责人，记录提交对象、实际提交时间、外部参考号、预计回复时间及跟进结果。负责人不同于创建人、最后修改人或本次操作人。

跟进记录采用简单的追加记录，保留操作者及时间，不因每次催办变更主状态。内部备注与客户可见说明分开；客户不直接获得内部代理渠道、成本信息。负责人离岗或转交时记录交接，避免无人跟进。

### B2. 取消闭环

区分三种情况：

1. 草稿删除／未对外提交的撤回：可沿用受控取消，保留记录。
2. 已提交船司／代理：提出取消后等待外部结果，不能立即表示外部订舱已取消。
3. 已收到 订舱确认单／已创建运输：取消申请必须连同 订舱确认单 和运输影响一起处理。

建议流程为“提出申请 → 操作核实及对外申请 → 登记确认／拒绝结果 → 同步相关业务”。申请记录应包含原因、申请人、时间、外部结果、凭据及客户可见说明。

待取消期间的建档、发布及执行动作必须有明确限制，避免一边取消一边继续安排。取消成功后处理关联运输及 订舱确认单 有效性，保留历史文件与审计，不删除历史业务。取消失败时明确恢复何种可办理状态及后续动作。

如有取消费用，先记录外部费用说明与客户确认，不自动扣款或扩展到账务系统。截止时间仅作提示，不能由系统自行推断船司已接受取消。已开船等阶段是否允许申请，按第 10 节业务决策确定。

### B3. 订舱变更

对于已提交后的箱型箱量、船期、货物及服务变化，新增变更申请／处理记录，不直接覆盖原委托。

操作核实影响；涉及价格或服务承诺的变更交销售确认并取得客户确认，再处理对外变更和必要的 订舱确认单 修订。纯资料纠错与商务变更应区分。不得修改已接受报价快照来掩盖差异。

保留原值、拟改值、原因、申请人、处理结果及外部确认凭据。没有外部确认时不得展示成新舱位已经落实。第一轮不开放多票拆分订舱；第二轮也不能默认突破 V1 常规一报价一订舱约束。

### B4. 提箱／装柜交接

以 Shipment 承接后续安排，Booking 只聚合展示入口及结果。按实际承诺记录是否由货代安排拖车／装柜、执行责任方、计划时间地点、联系人、准备状态和交接备注。

先明确“客户需求 → 报价确认服务 → 实际执行责任”，再交接。客户自行安排时显示其责任和需要反馈的信息；货代安排时显示待安排／已安排等真实结果。

车牌、司机联系方式、箱封号等按履约阶段补充，不在初次订舱时全部强制填写。现有 Container 字段可复用，但拥有字段不等于已经具备安排流程。不得借此引入车队调度或海关申报系统。

## 8. 技术、安全与数据约束

- 沿用 NestJS／Prisma 模块化单体及已有权限，核心规则由服务端执行。
- Booking、订舱确认单、Shipment 保持独立对象；状态变更使用语义化动作，禁止任意设置状态。
- 租户与客户公司隔离覆盖详情、委托版本、导出、跟进、取消、变更及文件访问。
- 客户响应和导出使用显式字段白名单，排除内部备注、供应商信息、成本和非客户可见文件。
- 提交版本、取消确认、变更落实与敏感字段修改需审计；业务写入与审计尽量同事务完成。
- 并发提交、重复点击、订舱确认单 更新及运输建档必须防重复或检测冲突，不能由页面按钮禁用代替。
- 历史单缺少的新字段显示未知，不伪造历史提交快照、负责人、外部确认时间。
- 已有 订舱确认单 字段优先复用；提交快照、跟进／取消／变更记录按实际设计新增模型与迁移，本文不预定表结构。
- 不修改已应用迁移；涉及存量状态解释变化需给出迁移和兼容方案。
- 如服务端生成委托文件，复用现有对象存储及文件鉴权；需要后台生成时采用已有队列能力。

## 9. 验收标准

所有项目初始均为未验收。实现后记录测试版本、环境和证据，不以文档或截图代替真实持久化及权限验证。

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| A-01 | 报价转委托 | 已知信息正确继承，客户只补缺项，计划日期含义清晰 |
| A-02 | 草稿及提交 | 草稿可保存，缺项提交由服务端拦截并准确指向字段 |
| A-03 | 退回重提 | 新提交生成新版本；原版本、提交人及时间不被覆盖 |
| A-04 | 委托导出 | 导出与指定提交版本一致，无内部信息；跨客户／跨租户不可访问 |
| A-05 | 订舱确认单 完整录入 | ETA、码头、三类截止时间及实际接收时间可保存并正确回显；时区无偏移 |
| A-06 | 订舱确认单 内部与发布 | 内部文件不可被客户获取；发布后才可见有效版本，旧版本按既有权限规则处理 |
| A-07 | 运输继承 | 采用有效 订舱确认单 的确认信息；已建档不重复创建；缺项不伪造 |
| A-08 | 订舱确认单 修订 | 与运输差异可发现，确认更新留痕，ATD／ATA 不被覆盖 |
| A-09 | 阶段指引 | 各状态指引符合真实可执行动作，加载失败与空状态分开 |
| B-01 | 办理与转交 | 负责人、提交及跟进可追溯；客户不见内部备注 |
| B-02 | 取消成功 | 申请不等于成功，外部确认后正确处理 订舱确认单 与运输，历史记录保留 |
| B-03 | 取消失败／并发 | 外部拒绝可记录；待取消阶段无互相冲突的继续办理动作 |
| B-04 | 商务变更 | 价格／服务变化经过销售及客户确认，不篡改原报价与委托 |
| B-05 | 装柜交接 | 区分客户自行安排与货代安排，责任、时间地点和关联入口清楚 |

自动化应覆盖关键规则单元测试、真实数据库事务与租户／客户隔离集成测试，以及“提交 → 退回重提 → 对外办理 → 订舱确认单 内部登记 → 建运输 → 发布下载”的 E2E。第二轮再增加取消、变更和交接路径。相关 typecheck、lint、测试全部通过后，使用真实客户与操作账号进行业务 UAT。
