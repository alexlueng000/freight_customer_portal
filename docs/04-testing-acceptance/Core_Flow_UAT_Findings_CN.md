# 核心业务闭环 UAT 发现记录

> 目的：记录手工跑通 Rate -> Quote -> Booking -> Shipment -> Tracking -> Document -> Invoice 闭环过程中发现的产品、权限、流程和体验优化点。

## UAT-P0-013 固定模板导入无法承接真实客户复杂运价 Excel

- **发现时间**：2026-08-31
- **发现阶段**：Shipment 前核心流程问题复盘 / Pilot 可用性评估
- **发现页面**：运营后台 / 运价 Excel 导入
- **当前现象**：当前导入能力主要围绕平台固定长表模板，V2 需求虽然增加业务友好的宽表模板，但仍隐含要求客户先按平台字段和 Sheet 结构整理文件。现实客户运价表通常包含多层表头、合并单元格、多个 Sheet、说明行、横向箱型、不同币种、附加费区块和自定义字段，不会按平台模板重新维护。
- **问题判断**：这是 Pilot 上线阻断项，不是普通导入体验优化。若客户必须先人工搬运或重做 Excel，导入功能无法降低迁移成本，客户不会持续使用 Rate 模块，后续 Quote、Booking 和 Shipment 链路也失去数据入口。
- **P0 产品决策**：
  - 支持直接上传客户现有 Excel，平台模板仅作为推荐方式，不作为导入前提。
  - 支持选择 Sheet、定位表头、字段 Mapping、箱型价格映射、附加费映射和数据清洗。
  - Mapping 结果必须预览并由用户确认，存在 ERROR 时不得写入任何业务数据。
  - 支持保存租户级或供应商级 Mapping Profile，使同来源文件后续可重复导入。
  - 使用真实客户样本建立回归样本库；不能只用平台生成的理想模板验收。
  - 保留 V1/V2 标准模板兼容，但不得把“请下载最新模板重新填写”作为复杂文件的唯一处理方式。
- **验收标准**：
  - 至少选取 3 类结构明显不同的脱敏真实货代运价工作簿完成导入验收。
  - 用户无需手工复制到平台模板，即可完成 Sheet/表头选择和关键字段映射。
  - 系统正确标准化一行多箱型、币种、有效期和附加费，并在写库前展示预览。
  - 保存 Mapping Profile 后，同来源下一期运价文件可复用配置，只处理新增或变化列。
  - 错误能定位到原 Sheet、原行、原列及标准字段；存在错误时整批不写库。
  - 自动化测试覆盖多 Sheet、多层/偏移表头、空白说明行、横向箱型、附加费和 Mapping Profile 租户隔离。
- **优先级**：P0 / PILOT BLOCKER
- **状态**：OPEN

## UAT-OPT-001 仪表盘未按角色展示差异化内容

- **发现时间**：2026-08-31
- **发现阶段**：核心业务闭环手工测试启动阶段
- **发现页面**：运营后台 / 仪表盘
- **当前现象**：不同角色登录后看到的仪表盘指标、待办列表和快捷操作基本一致。例如销售、操作、财务均看到同一组“待订舱、待放 SO、近期离港、未结账单”和相同待办。
- **问题判断**：这是不合理的。仪表盘是角色工作台，应反映当前用户的职责、权限和待办优先级，而不是展示全局通用模拟看板。
- **业务影响**：
  - 销售用户会看到与报价和客户跟进无关的操作/财务待办，干扰日常工作。
  - 操作用户需要优先看到订舱审核、SO 放单、Shipment、箱号和节点维护，不应被销售/财务指标稀释。
  - 财务用户需要优先看到待开票、已开票待确认、逾期应收、待标记收款，不应以订舱运营任务为主。
  - 客户用户如果看到内部运营指标或快捷入口，将带来权限边界和信息泄露风险。
- **建议修正方向**：
  - `TENANT_ADMIN`：展示全租户总览、异常待办、用户/客户/权限入口和关键业务指标。
  - `SALES`：展示待发送报价、报价接受率、客户待跟进、即将过期报价和创建报价入口。
  - `OPERATION`：展示待审核订舱、待放 SO、待创建 Shipment、待更新 tracking、异常/临近 ETD shipment。
  - `FINANCE`：展示待开票、待客户确认、逾期应收、待标记收款、发票金额汇总。
  - `CUSTOMER_ADMIN`：展示本公司报价、订舱、在途 shipment、可下载单证、待确认账单，并保留子账号管理入口。
  - `CUSTOMER_USER`：仅展示本公司授权业务数据，不展示账号管理、内部运营、全局财务汇总或 admin 快捷入口。
- **验收标准**：
  - 使用 6 个 demo 角色分别登录，仪表盘标题、指标卡、待办列表和快捷操作均按角色职责区分。
  - 服务端返回的数据受 tenant、role 和 customerCompany scope 约束。
  - 客户角色不能通过仪表盘看到其他客户公司或内部运营数据。
  - 自动化测试至少覆盖销售、操作、财务、客户用户四类仪表盘权限/内容差异。
- **优先级**：P1
- **状态**：OPEN

## UAT-OPT-005 报价状态需要颜色区分

- **发现时间**：2026-08-31
- **发现阶段**：Rate → Quote 手工测试
- **发现页面**：客户门户 / 报价详情、客户门户 / 我的报价、运营后台 / 报价
- **当前现象**：报价状态是关键业务信号，但页面上默认以灰色标签显示，不利于快速区分待销售确认、已发送、已接受、已拒绝、已过期等状态。
- **问题判断**：这是体验优化项。报价状态决定客户能否下载 PDF、接受/拒绝报价、创建订舱，也影响销售是否需要审核发送或标记过期，应该在列表和详情中有一致的视觉区分。
- **修正记录**：
  - 新增统一报价状态文案与颜色映射。
  - `DRAFT` 使用 warning，提示待销售确认；`SENT` / `VIEWED` 使用 info，表示客户可继续决策；`ACCEPTED` / `BOOKED` 使用 success，表示流程已推进；`REJECTED` 使用 danger；`EXPIRED` 使用 warning；`CANCELLED` 使用 neutral。
  - 客户侧报价列表、客户侧报价详情、后台报价列表和后台报价详情已统一使用该映射。
- **验收标准**：
  - 同一 Quote 状态在客户侧和后台展示一致的中文文案与颜色。
  - 状态颜色不替代服务端状态机和权限控制，仅作为可读性增强。
  - `lint` 和 `typecheck` 通过。
- **优先级**：P2
- **状态**：RESOLVED

## UAT-OPT-006 后台报价列表不应直接审核并发送

- **发现时间**：2026-08-31
- **发现阶段**：Rate → Quote 手工测试
- **发现页面**：运营后台 / 报价列表
- **当前现象**：后台报价列表中，`DRAFT` 报价可直接点击“审核并发送”，无需进入报价详情查看客户、航线、箱量、费用明细、销售价、有效期或改价记录。
- **问题判断**：这是不合理的。报价发送给客户前属于重要业务确认动作，销售应先进入详情页核对报价快照和费用明细，再从详情页执行发送；列表页的一键发送容易造成误发、漏审或未核价即发送。
- **业务影响**：
  - 销售可能只看列表摘要就发送正式报价，未发现费用明细、箱量、有效期或客户信息错误。
  - 手工改价原因、成本快照和利润空间没有被审阅，削弱报价审核闭环。
  - 报价误发后会进入客户可下载、可接受/拒绝的状态，可能直接影响后续订舱。
- **建议修正方向**：
  - 后台报价列表的操作列改为“查看/审核”，点击进入报价详情页。
  - 仅在报价详情页保留“发送客户”动作，并让销售在详情中完成明细核对、必要改价和过期检查。
  - 如后续确需列表批量发送，必须增加二次确认、权限校验和审计说明，并限定为已完成审核的状态。
- **修正记录**：
  - 后台报价列表的 `DRAFT` 操作已调整为进入详情审核，不在列表直接调用发送接口。
  - 正式发送保留在报价详情页，并继续受服务端状态机、`quote.manage` 权限和 AuditLog 约束。
- **验收标准**：
  - `DRAFT` 报价在后台列表页不能直接发送客户。
  - 销售必须打开报价详情页后才能执行发送动作。
  - 发送前详情页可见报价客户、航线、箱型箱量、费用明细、总额、有效期和状态。
  - 发送动作仍由服务端状态机和 `quote.manage` 权限控制，并写入 AuditLog。
- **优先级**：P1
- **状态**：RESOLVED

## UAT-OPT-007 报价详情页销售确认语义不清

- **发现时间**：2026-08-31
- **发现阶段**：Rate → Quote 手工测试
- **发现页面**：运营后台 / 报价详情
- **当前现象**：报价详情页右上角主操作为“发送客户”，页面没有明确标识这里就是销售审核/销售确认的位置。测试人员看到状态“待销售确认”后，不容易判断应在哪里完成确认。
- **问题判断**：这是体验和流程语义优化项。当前后端动作本质上是销售确认后发送正式报价，但前端文案只强调“发送”，弱化了审核确认语义。
- **业务影响**：
  - 销售或测试人员可能误以为页面缺少销售确认功能。
  - “待销售确认”状态与“发送客户”按钮之间的业务关系不够直观，增加培训和测试解释成本。
  - 报价审核动作的重要性被按钮文案弱化，容易被理解为普通通知发送。
- **建议修正方向**：
  - 将详情页 `DRAFT` 状态下的主按钮从“发送客户”调整为“确认并发送客户”。
  - 在状态区域或按钮附近增加简短提示，例如“核对报价明细后确认发送，客户随后可下载 PDF、接受或拒绝报价”。
  - 点击确认发送时增加二次确认弹框，弹框中展示报价编号、客户、航线和总额，并提示发送后的客户可操作范围。
  - 保留“调整价格”“标记过期”等审核前动作，但视觉上明确“确认并发送客户”是完成销售确认的主路径。
- **修正记录**：
  - 后台报价详情页 `DRAFT` 主按钮已改为“确认并发送客户”。
  - 点击主按钮后先弹出二次确认框，确认后才调用发送接口。
- **验收标准**：
  - `DRAFT` 报价详情页能清楚看出销售确认入口。
  - 操作文案同时表达“确认”和“发送客户”两个业务含义。
  - 发送客户前必须经过二次确认，确认框展示关键报价摘要并说明客户后续可下载 PDF、接受或拒绝报价。
  - 客户侧仍只看到待销售确认或正式报价状态，不暴露内部成本和审核动作。
- **优先级**：P2
- **状态**：RESOLVED

## UAT-OPT-008 客户接受报价需要二次确认

- **发现时间**：2026-08-31
- **发现阶段**：Rate → Quote 手工测试
- **发现页面**：客户门户 / 报价详情
- **当前现象**：客户在报价详情页可直接点击“接受报价”，当前操作会立即调用接受接口，没有二次确认。
- **问题判断**：这是不合理的。接受报价是客户侧关键业务承诺动作，会把 Quote 推进到 `ACCEPTED`，并允许后续基于报价创建订舱，应防止误点。
- **业务影响**：
  - 客户可能未复核报价编号、航线、有效期和总金额就误接受报价。
  - 错误接受会影响销售和操作后续跟进，也可能产生不必要的订舱沟通。
  - 测试人员难以判断系统是否把客户确认动作作为关键决策处理。
- **修正记录**：
  - 客户报价详情页点击“接受报价”后先弹出二次确认框。
  - 确认框展示报价编号、航线、有效期和报价总额，并说明接受后可创建订舱。
  - 只有点击“确认接受”后才调用接受报价接口。
- **验收标准**：
  - `SENT` / `VIEWED` 报价点击“接受报价”不会立即改变状态。
  - 二次确认框中可见报价编号、航线、有效期和总额。
  - 点击“取消”关闭弹框且不调用接受接口。
  - 点击“确认接受”后由服务端状态机和 `quote.accept` 权限完成状态变更。
- **优先级**：P1
- **状态**：RESOLVED

## UAT-NOTE-002 测试计划修正：Sales 不作为后台运价维护角色

- **发现时间**：2026-08-31
- **发现阶段**：核心业务闭环手工测试计划校准
- **涉及角色**：`SALES`
- **当前确认**：Sales 账号访问后台运价页显示“权限不足”符合当前批准需求和实现，不应作为缺陷记录。
- **文档依据**：
  - PRD：Sales 负责客户、报价、销售价格、客户订单/历史报价；客户侧负责查价并提交报价申请。
  - 角色流程文档：销售负责审核 Quote、必要时调价并发送正式报价。
  - 开发进度文档：后台 `rate.read` / `rate.manage` 仅平台/租户管理员可访问；客户查价使用独立销售价响应模型。
  - Seed 权限：`SALES` 拥有 `quote.read` / `quote.manage`，但不拥有 `rate.read` / `rate.manage` / `rate.search`。
- **测试计划修正**：
  - 后台 Rate 创建、编辑、导入、筛选：使用 `TENANT_ADMIN`。
  - 客户查价：使用 `CUSTOMER_ADMIN` 或 `CUSTOMER_USER`。
  - Sales 测试重点：查看自己负责客户的 Quote、审核/手工调价/发送 Quote、查看相关 Booking/Shipment/Document/Invoice。
- **状态**：CONFIRMED

## UAT-OPT-009 前端错误提示未展示字段级校验明细

- **发现时间**：2026-08-31
- **发现阶段**：Booking 资料提交手工测试
- **发现页面**：客户门户 / 订舱详情
- **当前现象**：客户在 Draft Booking 页面填写不合法资料后点击“提交审核”，页面顶部只显示通用错误 `Request validation failed`。浏览器 Network 响应中实际包含字段级校验明细，例如 `bookingContactEmail must be an email`，但页面没有把该明细展示给用户，也没有定位到对应表单字段。
- **问题判断**：这是不合理的。后端已经返回了可操作的校验原因，但前端只展示总括错误，导致业务用户不知道该修正哪个字段，只能依赖开发者工具排查。对于 Booking、Rate Import、Quote、Invoice 等关键表单，字段级错误必须在界面上可见，不能只停留在 API 响应里。
- **业务影响**：
  - 客户提交订舱资料失败后无法自助修正，容易反复提交或求助客服/操作人员。
  - UAT 和真实试点中会被误判为“系统报错但不知道错在哪里”，降低客户门户可信度。
  - 如果只显示英文后端校验文案，业务用户仍难以理解，需要有中文字段名和可执行修改建议。
- **建议修正方向**：
  - 统一前端 API 错误解析逻辑，读取响应中的 `details.errors` 或等价字段，并在页面错误区展示具体原因。
  - 对表单类页面优先将字段级错误挂到对应输入项下方，例如“联系人邮箱：请输入有效邮箱地址”。
  - 顶部错误摘要应保留，但需要提示“请修正以下字段”，并列出最多若干条关键错误，避免只显示 `Request validation failed`。
  - 建立后端字段名到中文表单标签的映射，至少覆盖 Booking 提交、客户资料、用户管理、Rate 创建/导入、Quote 改价和 Invoice 创建。
  - 保留服务端 DTO 校验作为最终边界；前端 Zod 校验只用于提前反馈，不能替代后端校验展示。
- **验收标准**：
  - 在 Booking 详情页输入非法邮箱并提交时，页面可见中文字段级错误，不需要打开 DevTools。
  - 通用 API 错误解析能兼容 `message`、`details.errors` 和领域错误码，不泄露堆栈或敏感信息。
  - 字段级错误展示不破坏 loading、保存中、权限不足和业务状态错误展示。
  - 自动化测试至少覆盖一个 Booking 非法字段提交场景，断言页面展示具体校验原因。
- **优先级**：P1
- **状态**：OPEN

## UAT-OPT-010 Booking 操作按钮未按权限隐藏

- **发现时间**：2026-08-31
- **发现阶段**：Booking 内部审核手工测试
- **发现页面**：运营后台 / Booking 详情
- **发现角色**：`SALES`
- **当前现象**：Sales 拥有 `booking.read`，可以查看自己负责客户的 Booking，但不拥有 `booking.manage`。页面仍根据 Booking 状态展示“开始审核”“确认订舱”“拒绝”“取消”等操作按钮。Sales 点击后，服务端正确返回 `You do not have permission to perform this action`。
- **问题判断**：服务端授权边界正确，但前端操作可见性错误。用户不应看到自己必然无权执行的主操作按钮；这种“可点击后才报无权限”的设计会误导用户对角色职责的理解，并制造可避免的失败请求。
- **业务影响**：
  - Sales 会误以为自己负责 Booking 审核或确认，与当前批准的角色分工冲突。
  - 页面先鼓励操作、再用英文错误拒绝，造成明显的产品体验断裂。
  - UAT 人员可能误判为后端权限配置错误，增加排查和培训成本。
  - 如果其他模块采用同样的“只按状态、不按权限”渲染方式，会持续出现 Rate、Shipment、Document 和 Invoice 的死按钮。
- **当前权限事实**：
  - `SALES`：拥有 `booking.read`，可以查看相关 Booking。
  - `OPERATION`：拥有 `booking.read`、`booking.manage` 和 `shipment.create`，负责审核、确认、拒绝、取消、SO 与 Shipment 操作。
  - 服务端 `review / confirm / reject / cancel` 端点继续由 `booking.manage` 强制保护，不能依赖前端隐藏按钮替代授权。
- **建议修正方向**：
  - 前端 Auth Context 应暴露服务端返回的有效 permissions，业务页面按 permission + object status 共同判断操作可见性。
  - Booking 详情只有在用户拥有 `booking.manage` 且状态允许时，才显示审核备注和审核/确认/拒绝/取消按钮。
  - 只有拥有 `shipment.create` 且 Booking 为 `SO_RELEASED` 时，才显示“创建 Shipment”。
  - 无管理权限的 Sales 保持只读视图；可显示“由操作人员处理”之类的角色提示，但不能展示禁用或可点击的死按钮。
  - 保留服务端 Guard 和权限负向测试，前端控制只用于正确体验，不能成为安全边界。
  - 统一扫描 Customer、Rate、Quote、Booking、Shipment、Document、Invoice 页面，找出所有仅按状态渲染而未按权限控制的操作。
- **验收标准**：
  - Sales 打开 `SUBMITTED` / `UNDER_REVIEW` / `CONFIRMED` Booking 时，不显示审核备注和任何 `booking.manage` 操作。
  - Operation 在相同状态下看到符合状态机的操作按钮并能正常执行。
  - 用户即使绕过前端直接调用端点，Sales 仍收到 403，Operation 正常执行。
  - 权限变化或用户停用后重新获取会话，页面操作可见性与服务端有效权限一致。
  - 至少增加 Sales 只读和 Operation 可操作两组前端/E2E 测试。
- **优先级**：P1
- **状态**：OPEN

## UAT-OPT-011 “开始审核”与“确认订舱”形成无意义双步骤

- **发现时间**：2026-08-31
- **发现阶段**：Booking 内部审核手工测试
- **发现页面**：运营后台 / Booking 详情
- **发现角色**：`OPERATION`
- **当前现象**：Operation 打开 `SUBMITTED` Booking 后先点击“开始审核”，状态变为 `UNDER_REVIEW`；页面内容、业务字段、审核信息和责任人均无变化，只是把按钮替换为“确认订舱/拒绝/取消”。Operation 随后必须再次点击“确认订舱”才能进入 `CONFIRMED`。
- **问题判断**：当前 `SUBMITTED → UNDER_REVIEW → CONFIRMED` 是形式上的双步骤，不具备真实审核价值。系统没有在“开始审核”时完成认领、分配责任人、锁定记录、补充内部资料、执行检查清单或形成客户可见反馈，因此该动作只增加一次点击和一个难以解释的中间状态。
- **业务影响**：
  - Operation 对同一页面连续点击两次才能完成一个业务决定，降低处理效率。
  - 用户难以理解“已提交”“审核中”“已确认”的实际差异，培训成本增加。
  - 自动化测试和状态机复杂度增加，但没有带来对应的业务控制价值。
  - 如果 Operation 点击“开始审核”后离开，Booking 会长期停留在 `UNDER_REVIEW`，但系统又没有负责人或超时机制解释谁在处理。
- **V1 产品决策**：
  - 合并无业务内容的“开始审核”和“确认订舱”。
  - Operation 在 `SUBMITTED` Booking 详情直接执行“确认订舱”或“拒绝订舱”。
  - 新流程优先采用 `SUBMITTED → CONFIRMED` 或 `SUBMITTED → REJECTED`。
  - `UNDER_REVIEW` 如已存在历史数据，应保留兼容读取和迁移策略，不应直接删除已使用的枚举值。
  - 如果未来确实需要 `UNDER_REVIEW`，必须同时引入明确业务含义，例如处理人认领/分配、审核清单、内部补料、处理 SLA 或记录锁定；不能只保留一个状态跳转按钮。
- **页面优化要求**：
  - `SUBMITTED` 页面直接显示“确认订舱”“拒绝订舱”和符合权限的取消动作。
  - 确认前使用二次确认框，展示 Booking 编号、客户、航线、ETD、箱型和箱量。
  - 拒绝必须填写原因；拒绝原因是否客户可见需使用独立字段或明确规则。
  - 确认成功后页面直接进入 `CONFIRMED`，并展示下一步“上传/放出 SO”。
  - 不创建内容完全相同的“开始审核后页面”。
- **服务端要求**：
  - 状态转换仍由服务端校验并写入 AuditLog。
  - 合并动作不能通过前端连续调用两个状态端点伪装成原子操作；应提供清晰的单一确认/拒绝命令。
  - 并发确认、重复点击和非法状态必须返回稳定、可理解的领域错误。
- **验收标准**：
  - Operation 从 `SUBMITTED` Booking 最多一次业务确认即可进入 `CONFIRMED`。
  - 页面不再要求先点击没有附加业务内容的“开始审核”。
  - Sales 等无 `booking.manage` 权限角色仍保持只读。
  - 确认、拒绝、重复确认、并发操作和 AuditLog 均有自动化测试。
  - 历史 `UNDER_REVIEW` 数据仍可读取，并有明确的继续处理或迁移方式。
- **优先级**：P0
- **实施时机**：当前测试闭环完成后，与 Booking 表单减负优化一起实施。
- **状态**：OPEN

## UAT-OPT-012 SO 来源不清且“上传”和“放给客户”被合并

- **发现时间**：2026-08-31
- **发现阶段**：Booking Confirmed → SO → Shipment 手工测试
- **发现页面**：运营后台 / Booking 详情
- **发现角色**：`OPERATION`
- **当前现象**：Booking 进入 `CONFIRMED` 后，页面直接显示文件选择框和“上传并放出 SO”按钮，但没有说明 SO 由谁提供、Operation 应从哪里取得，也没有区分“文件上传成功”和“授权客户查看”两个动作。测试人员容易误以为 SO 应由本系统生成或自动获取。
- **业务定义**：SO（Shipping Order，订舱确认书/放舱单）通常由船公司、订舱代理或 NVOCC 在舱位确认后通过网站、邮件或其他外部渠道返回。当前 V1 不包含船公司订舱 API/EDI，也不自动生成或抓取 SO；Operation 需要先在系统外取得文件，再上传到门户。
- **问题判断**：
  - 页面缺少文件来源和业务前置说明，操作人员无法从产品本身理解下一步。
  - “上传”和“放给客户”语义不同：上传是内部文件归档，放出是改变 `customerVisible` 的授权动作。
  - 将二者合并会使未经内部核对的文件立即对客户可见，增加错文件、错误版本或敏感信息泄露风险。
  - 当前用 `SO_RELEASED` 同时表达文件存在和客户已可见，无法清晰区分处理中间状态。
- **优化要求**：
  - 页面标题改为“上传船公司/订舱代理返回的 SO”。
  - 增加说明：“请从船公司网站、邮件或订舱代理处取得订舱确认文件后上传；系统不会自动生成 SO。”
  - 支持记录 SO Number、来源类型、船公司/代理、收到时间、CY Cut-off、SI Cut-off、VGM Cut-off 等已批准字段。
  - 将“上传 SO”和“放给客户”拆成两个受控动作；上传后默认仅内部可见，核对无误后再放出。
  - 放出前二次确认 Booking、客户、文件名、版本和客户可见范围。
  - 上传新版本时保留版本记录，明确旧版本是否 `SUPERSEDED`，避免客户下载过期 SO。
  - 页面显示当前 SO 的来源、上传人、上传时间、版本和客户可见状态。
- **建议状态语义**：

  ```text
  CONFIRMED
  → 等待外部 SO
  → SO 已上传（内部可见）
  → SO 已放给客户
  → 可创建 Shipment
  ```

  是否新增 Booking 状态或改用 Document 状态/可见性表达，应在实施前结合批准 ERD 评估；不得为页面文案直接增加未经设计的数据枚举。
- **安全要求**：
  - 客户只能读取 `customerVisible=true`、ACTIVE 且属于当前 tenant/customer scope 的 SO。
  - 对象存储 Key 不作为授权边界。
  - 上传、版本替换和客户可见性变化均写入 AuditLog。
  - 放出动作要求明确权限，不能因拥有文件上传权限自动获得客户发布权限。
- **验收标准**：
  - Operation 无需查阅外部文档即可理解 SO 的来源和取得方式。
  - 上传文件后客户默认不可见；Operation 核对并确认放出后客户才可下载。
  - 错文件可在未放出前替换或作废，不向客户暴露。
  - 新旧版本、上传人、时间和可见状态可追溯。
  - 自动化测试覆盖内部上传、客户不可见、放出后可见、旧版本不可见、跨租户拒绝和无发布权限拒绝。
- **优先级**：P0
- **实施时机**：当前测试闭环完成后，与 Booking/SO/Shipment 流程优化一起实施。
- **状态**：OPEN

## UAT-DEFECT-003 客户创建后缺少公司信息编辑能力

- **发现时间**：2026-08-31
- **发现阶段**：客户主数据手工测试
- **发现页面**：运营后台 / 客户详情
- **当前现象**：Tenant Admin 新建客户公司后，可以进入客户详情并继续新增联系人，但页面缺少编辑客户公司基础信息的入口；后端当前也未暴露客户公司更新接口。
- **问题判断**：这是不合理的。客户主数据创建后仍需要维护公司名称、简称、国家/地区、税号、销售负责人、账期、信用额度、默认加价规则和状态等信息；测试不能只验证“新建成功”，还必须验证“新建后可维护”。
- **业务影响**：
  - 录入错误无法通过正常业务界面修正，容易诱导直接改库。
  - 客户账期、信用额度、销售负责人或默认加价规则变化后无法维护，会影响后续 Rate、Quote、Booking 和 Billing 流程。
  - 客户状态变更无法闭环验证，可能导致启用、停用、冻结等权限与业务边界漏测。
- **建议修正方向**：
  - 增加受 `customer.manage` 保护的客户公司编辑能力，例如 `PATCH /api/v1/customers/:id`。
  - 仅允许编辑 V1 已批准的客户主数据字段；客户代码如需不可变，应在界面和接口错误中明确说明。
  - 更新必须强制 tenant scope，客户类型账号不得编辑客户公司主数据。
  - 编辑账期、信用额度、默认加价规则、状态和销售负责人等敏感字段时写入 AuditLog before/after。
  - 运营后台客户详情页增加清晰的编辑入口，并覆盖保存中、成功、失败、权限不足和校验错误状态。
- **验收标准**：
  - Tenant Admin 可在新建客户后从详情页编辑允许字段，刷新后仍展示最新值。
  - 非 `customer.manage` 角色无法通过界面或 API 编辑客户公司。
  - 跨租户 Customer ID 更新失败，不泄漏目标客户所属租户信息。
  - 客户代码不可编辑或受控编辑规则明确，租户内唯一性仍被验证。
  - 编辑操作写入审计日志，且不记录密码、Token 或无关敏感信息。
  - 自动化测试覆盖创建后编辑、权限拒绝、跨租户拒绝、字段校验和审计记录。
- **优先级**：P1
- **状态**：OPEN

## UAT-OPT-004 客户详情页缺少客户登录账号创建与管理入口

- **发现时间**：2026-08-31
- **发现阶段**：客户主数据与账号开通手工测试
- **发现页面**：运营后台 / 客户列表、客户详情、用户管理
- **当前现象**：系统已有客户用户模型和“管理 / 用户”页面，可在新建用户时创建 `CUSTOMER_ADMIN` / `CUSTOMER_USER` 并绑定客户公司；但在客户列表或客户详情页只展示“联系人 / 用户”数量，没有面向当前客户公司的“新增登录账号”或“管理客户账号”入口。同时，全局用户管理的“管理用户”抽屉只允许调整角色和账号状态，不能查看/修改客户账号所属 CustomerCompany。测试人员从客户维护流程进入时，容易误判为客户创建后不能给客户开通系统账号；从用户管理流程进入时，也无法修正客户账号绑定关系。
- **问题判断**：这是重要的流程可发现性缺口。V1 的客户门户要求客户公司人员可登录系统查价、报价、订舱、跟踪和看账单；客户主数据、联系人和客户登录账号虽然是不同概念，但运营人员通常会在客户详情中完成账号开通或跳转到已按该客户过滤的用户管理页面。
- **业务影响**：
  - 新客户开通流程不完整，创建客户公司后无法顺手完成客户 Portal 账号开通。
  - 联系人和登录账号容易被混淆；联系人不一定能登录，客户用户必须绑定 CustomerCompany 和客户角色。
  - 多客户场景下，如果只能在新建时去全局用户页手动选择客户公司，容易选错公司；创建后又没有正常入口修正绑定，增加跨客户数据范围配置风险。
  - UAT 可能只验证客户公司和联系人，不验证客户真实登录闭环。
- **建议修正方向**：
  - 在客户详情页的“客户用户”计数旁或页面主操作区增加“新增客户账号”入口。
  - 新增账号表单应默认锁定当前 CustomerCompany，只允许选择 `CUSTOMER_ADMIN` / `CUSTOMER_USER` 角色。
  - 提供“查看客户账号”入口，跳转到 `/admin/users` 并按当前客户公司过滤，或在客户详情中直接展示该客户下的用户列表。
  - 用户管理的编辑抽屉应展示客户账号当前所属公司；是否允许改绑 CustomerCompany 需要产品明确。如允许改绑，必须记录 AuditLog before/after，并校验不能把客户账号改绑到其他租户；如不允许改绑，界面需明确说明“所属客户公司不可在此修改”，并提供禁用态字段或跳转说明。
  - 明确区分“联系人”和“客户登录账号”的文案，避免把普通联系人误认为可登录用户。
  - 服务端仍以 `user.manage` 权限、tenant scope、角色类型和 CustomerCompany 绑定校验作为最终边界。
- **验收标准**：
  - Tenant Admin 从客户详情页可为当前客户公司创建客户登录账号，创建后该客户的用户数量增加。
  - 从客户详情创建账号时，客户公司绑定不可被前端随意改成其他客户；即使篡改请求，后端也必须按当前租户和合法 CustomerCompany 校验。
  - 在用户管理编辑客户账号时，必须清晰展示所属客户公司；若产品允许改绑，应能受控改绑并写入审计；若产品不允许改绑，应明确不可修改原因，不能让用户以为系统遗漏字段。
  - 客户账号创建后可使用租户代码、邮箱和初始密码登录，并进入 `/portal`。
  - 客户账号只能查看所属 CustomerCompany 的 Rate/Quote/Booking/Shipment/Document/Invoice 数据。
  - 内部角色不能被分配给客户用户，客户角色不能被分配给内部用户。
  - 自动化测试覆盖客户详情创建客户账号、全局用户页绑定客户公司、客户账号所属公司展示或受控改绑、跨租户或跨客户绑定失败，以及客户账号登录后的数据范围。
- **优先级**：P1
- **状态**：OPEN
